# Private-content v2 wire contract

**Status:** normative engineering supplement to the [implementation proposal](private-offers-and-deliveries.md), [implementation in progress](private-offers-implementation.md), not enabled. Anchor: `135e4ea0bd5330f7ab0272d501aa83a718edc777`. This closes the independent review's message-mapping, public-schema and delivery-binding gaps without changing the approved lifecycle or main's author roles.

## 1. Main's event rules remain authoritative

**Identity distinction:** v2 `job_id` in content/routing is the random `job` value. Main’s internal `job_id` often means the OFFER event ID. Keep the latter semantic in receipt `offer_id`, root references, invoice `payment_id`, contribution tuple and existing payment/idempotency keys; do not substitute the new random routing ID silently. Persist both with distinct names in v2.

Inherit lifecycle authors, claim/award eligibility, capability matching, deadline checks, feedback terminality, buyer verification and pay-once rules from `docs/protocol-v1.md:55`, `:383`, `:566`, `:598`, `:662`, `:700` and `:723 @135e4ea`. Encryption never grants a new role or permits a message at a phase where its existing event is invalid. A wrapper is transport, not a lifecycle event.

The following is the complete content-type mapping. A private content reference is the pair of singleton tags `content-id` and `content-commitment` on the signed carrier. Neither may occur alone. Each carrier has at most one content envelope; multiple explanations/review artifacts are fields inside that envelope, not additional ambiguous references.

| Content type | Signed public carrier / author | Phase and subject | Recipient scope |
| --- | --- | --- | --- |
| `task` | OFFER 3401 / buyer | Initial complete task; before claims. Initial envelope `offer_id=null`; signed OFFER pins job ID and content commitment. | Targeted: buyer, target, Maxplayer. Open-pool initial task remains public instead. |
| `claim_details` | CLAIM 3402 / claiming seller | Existing claim; private dispatch/model details, not a new claim action. Root offer required; `award_id=null`. | Buyer, this claimant, Maxplayer. Other candidates receive no copy. |
| `progress` | FEEDBACK 3404 / seller | Only the phases/statuses already valid on main. After award use exact award ID; before award retain main's refusal/release/error rules, not an invented work-progress phase. | Buyer, authoring candidate before selection; buyer, selected seller after selection; plus Maxplayer. |
| `feedback` | FEEDBACK 3404 / seller | Existing refusal/release/error explanation; same authorization as progress carrier, status/reason decide lifecycle effect. | Same as preceding row. |
| `answer` | RESULT 3403 / awarded seller | After the valid award; exact offer and award; Git or inline delivery. | Buyer, selected seller, Maxplayer. |
| `rejection` | REJECT 3407 / awarding buyer | Exact rejected RESULT and its delivery identity; existing rejection semantics. | Buyer, selected seller, Maxplayer. |

There is **no standalone `followup` or `review` transport type** in this release. Follow-up work is a new OFFER containing a `task`; prior-context references belong in that new task. No content edit mutates the task or required inputs under an existing claim. Review material is integrated as an artifact, as below, not a new public event kind or a reviewer-authored FEEDBACK.

### 1.1 Review artifact integration

Keep review initiation/authorization in the existing review integration; this spec does not invent a reviewer role in the trade lifecycle. A participant may include a received review artifact in its own already-valid carrier: buyer task context in OFFER; seller refusal explanation in FEEDBACK; seller delivery assessment in RESULT; buyer rejection assessment in REJECT. Carrier author remains buyer/seller, **not** the reviewer. No extra progress event is synthesized merely to obtain a carrier.

For private jobs, review findings/excerpts are encrypted within that carrier's body or stored as a private Git file whose pinned manifest entry is in that body. The common carrier commitment binds the exact received artifact bytes. Preserve any original reviewer signature and verify it against the reviewer identity configured by the existing review integration; do not relabel an unsigned artifact as reviewer-authenticated. In the absence of such evidence, it is a participant-provided artifact, not an authenticated third-party verdict.

Each artifact has `subject={offer_id,task_content_id?,task_content_commitment?,award_id?,result_event_id?,delivery_kind?,delivery_integrity_hash?}`. Task refs are mandatory for targeted-private task assessments; a public-task assessment binds its offer ID. An assessment of an already published result requires that result ID and its exact delivery identity. A pre-publication delivery assessment instead binds the pinned artifact identity and award; the enclosing RESULT must match it. It must not require its own future RESULT ID, which would be circular. Same distinction applies to pre-publication OFFER assessment: bind task commitment/job ID and resolve to the enclosing signed OFFER. Never silently apply an old assessment to a revised artifact.

Standalone review-service request/response transport remains owned by its existing adapter and does not become a trade-state transition. When carrying private job content, that adapter must preserve the agreed participant/Maxplayer access and exact subject binding; it must not publish plaintext. An integration lacking private transport cannot review a private job by falling back to its public path. Optional review unavailability follows the existing review policy, not a newly added privacy ACK gate.

### 1.2 Binding and recipients

For all non-initial-task envelopes, `offer_id` equals the carrier's root offer. `author` equals the carrier author and verified NIP-59 seal/rumor author. `job_id` equals the pinned OFFER's job ID. Before award, `award_id=null`; afterward it equals the validated award where the existing message belongs to the execution. `message_id` and commitment match the carrier. REJECT body additionally names its carrier's result ID. Recipient arrays contain exactly the applicable keys above, sorted by lowercase pubkey with duplicates removed; self-copies are included. Private claimed details are not disclosed to other candidates. Losing sellers cannot create execution content by attaching someone else's award ID.

Validate the carrier signature, its main-derived authorization and the content commitment before accepting decrypted content. A wrapper alone never establishes permission or overrides a signed carrier. Deduplicate logical IDs job-wide by `(job_id,message_id)`, regardless of author, exactly as in the parent spec. Repeated IDs must have identical committed bytes; reject conflicting carriers/copies, including collisions between two otherwise authorized authors. No application ACK is introduced.

## 2. Closed public schema

This section governs lifecycle kinds 3400–3407 for jobs with `visibility=private`, including their open-pool public discovery OFFER. It does not redefine seller profiles/heartbeats or unrelated relay events. Public jobs keep main's public content behavior with the v2 binding changes in §3; private-mode validation is never inferred from an arbitrary event's own claim—it is inherited from the validated root OFFER.

Only the tag rows below are allowed. Reject **every unlisted tag/subkey**, extra tag element, duplicate singleton, duplicate list value, invalid marker or invalid type, regardless of whether it appears content-bearing. Do not silently strip and accept signed unknown fields. Optional rows may be absent but never be represented as empty strings unless the shape explicitly requires an empty relay-hint slot. Extra top-level event keys outside the standard signed Nostr event representation are rejected by this protocol parser.

### 2.1 Scalar types and exact public vocabularies

- `H32`: exactly 64 lowercase hex characters. Event IDs, pubkeys, opaque job/content IDs, SHA-256 commitments.
- `Sig`: exactly 128 lowercase hex characters, valid Schnorr signature for the designated preimage when checked.
- `OID`: exactly 40 lowercase hex characters, with no abbreviation. This release retains main’s SHA-1 repositories and `ContributionBase` validation (`contribution.rs:112-140 @135e4ea`); SHA-256 repositories require a separate explicit migration. Integrity hash for Git uses the exact OID, not a second hash or padding.
- `U64`: canonical ASCII decimal integer 0..18446744073709551615, no sign/whitespace/leading zero except `0`. Enforce existing tighter amount/deadline/usage constraints too. Public numeric metadata is permitted, not evidence of truthful measurement.
- `Output`: `text | code | image | audio | video | data | archive | other`. Coarse category only. Original MIME/custom output description lives in targeted task content or in the intentionally public open task; decoded domain objects retain the original request for execution. No arbitrary string is emitted in the public `output` tag.
- `Family`: `claude-code | codex | cursor | goose`; `Agent`: `claude | cursor | codex`; `Capability`: `node | python | rust`. These closed initial sets follow `agent_presets.rs:13`, `:54` and `capability.rs:36 @135e4ea`. New entries require an explicit schema update; custom preset labels/model IDs remain in the content path below, never newly public by convention.
- `Status`: CLAIM uses only `processing`; AWARD/ACCEPT only `accepted`; REJECT only `rejected`; FEEDBACK only `progress | claim_released | refusal | error`.
- `Reason`: public FEEDBACK uses `below_rate | unsupported_version | mint_incompatible | at_capacity | execution_failed | delivery_failed | no_sentinel | other`; REJECT uses `other` or a fixed literal listed by the anchor protocol's §10.1 (verbatim enum, never runtime strings). Internal/unrecognized reasons map to `other`; detailed reason stays encrypted. Public classification still uses main's status/reason semantics; this explicitly closes private-mode extension strings.
- `Mint`: a configured accepted HTTPS mint URL, canonical as in the payment implementation, at most 2048 UTF-8 bytes, no credentials/query/fragment. It must match the claim's accepted set and local payment evidence; not an arbitrary descriptive URL.
- Private repo locator: configured HTTPS Git-host origin plus its fixed deployment route and server-generated buyer/job IDs. No user-supplied path, query, fragment or credentials. Route template is trusted deployment configuration; instance values are validated pubkey/H32 IDs. Ref: exactly `refs/heads/input/<H32>` or `refs/heads/delivery/<H32>`; public RESULT uses only a delivery ref.
- New tags or enum entries require explicit classification before deployment. Regex compliance alone does not make arbitrary free-form labels public. Fixed IDs/numbers still have covert-channel capacity; this is structural privacy for compliant clients, not prevention of deliberate exfiltration by authorized participants.

### 2.2 Common rows and reference shapes

Every row below has cardinality **1** unless another cardinality is shown. `root` means exactly `["e", offer_id, "", "root"]`; `reply` exactly `["e", result_id, "", "reply"]`; `claim-ref` exactly `["e", claim_id]`. Relay hints are empty; no descriptive relay URLs or extra marker fields. Actor keys come from validated signatures and referenced events, not tag ordering.

All eight kinds: `["t","maxplayer"]`, `["v","2"]`, `["job",H32]`.

Content pair (only where explicitly allowed below): `["content-id",H32]`, `["content-commitment",H32]`, both present or both absent. Their allowed cardinality is per carrier, not a blanket extension to every kind.

### 2.3 Per-kind tag tables

| Kind | Required rows beyond common | Optional / conditional rows; all other rows forbidden |
| --- | --- | --- |
| OFFER 3401 | `visibility=private`; `discovery=targeted\|open`; `output=Output`; `amount=<U64>,sat`; `param,deadline,<U64>` | `p,<target>` exactly 1 for targeted, absent for open. Targeted: content pair required, no `i`. Open: `i,<complete task>` exactly 1 and no content pair for initial task. `param,payment,none` 0..1 (absence=sat). `param,accepts-delivery,<git\|inline>...` 0..1, nonempty unique sorted set, default git. Approved capability rows below. `job-class,contribution` 0..1 and contribution rows below. Bound `delivery,git` / `repo,<locator>` / `branch,<delivery-ref>` all three or none. |
| CLAIM 3402 | `root`; `p,<buyer>`; `status,processing` | Seller mirror `p,<seller>` 0..1 (deduplicate if same identity). Exactly one of `creq,<request>` or `payment,none`, matched to OFFER. Capability rows below. Content pair 0..1 pair for `claim_details`. No free-form content. |
| AWARD 3405 | `root`; `claim-ref`; `p,<buyer>` and `p,<selected seller>`; `status,accepted` | No content pair, task, result, repo or readiness field. |

Numeric metadata echo below 0..N. |

`p` rows identifying buyer/seller collapse if the keys are equal; author/reference validation identifies roles without relying on tag order. Any pair of distinct keys must occur exactly once each. OFFER's initial public task is the explicit disclosure exception, limited to 16 KiB UTF-8; all other public event `content` strings for these private jobs are exactly empty. The encrypted body has the separately specified 16 KiB limit. RESULT carrier author must be the validated award's seller; payment amount must agree with the signed OFFER; RESULT output category must equal OFFER's public output category, and the decoded original requested output remains authoritative for execution/verification. Lexical validity alone is insufficient. The publisher chooses the coarse category explicitly; there is no implicit MIME-to-category conversion in this contract.

### 2.4 Capability, contribution, invoice and usage rows

**Capabilities.** OFFER permits singleton `param,agent,<Agent>` and `param,harness_family,<Family>`, and 0..1 `param,capability,<Capability>...` sorted unique nonempty list. CLAIM permits 0..1 each of `agents,<Agent>...`, `harness_family,<Family>...`, `capabilities,<Capability>...` with the same set rules. Main's capability/agent-consistency checks remain mandatory. Private targeted task content carries any original custom preset/model filter and reconstructs the request consumed by those same checks. CLAIM `claim_details` carries the seller's measured model/custom-preset values needed for matching, bound to that signed claim; a required detail that is unavailable makes the claim ineligible, never “no filter.” For open discovery, those non-enumerated filter values must be in the explicit public task envelope below; do not silently drop a buyer's filter. Pre-existing public heartbeat model labels are not changed by this job-content spec; never copy task-derived strings into them.

**Shared task payload.** Both targeted `type=task` bodies and public discovery use mandatory `text` (UTF-8 string), `requested_output` (nonempty UTF-8 original output string), and `dispatch` (object, possibly empty); optional `contribution` has exactly the schema below. In the targeted body these are top-level fields alongside the parent’s common identity/revision fields and mandatory `attachments` array; they are not nested in another schema envelope. `dispatch` permits only `agent` (nonempty original preset string), `harness_family` (Family), `harness_model` (nonempty original model/filter string), and `capabilities` (nonempty sorted unique Capability array). Each dispatch key is optional; absence means main’s no-preference/default semantics, not an empty string or null. Custom preset/model strings remain private for targeted tasks. Closed public enum tags are emitted only where the corresponding dispatch value belongs to that enum and must equal it; a custom agent preset is carried only in dispatch and must never be silently dropped from matching. Reject unknown or duplicate keys in these task objects. Attachments keep the parent’s exact manifest shape and validation. `claim_details` includes mandatory `dispatch` with this same field vocabulary, describing actual seller values rather than buyer preferences; main’s filter matching remains authoritative.

Public `Output` is an explicit coarse category chosen by the publisher, independently of the original `requested_output`; builders require that enum argument and never infer it from MIME strings. The same category is copied unchanged from OFFER to RESULT. The original requested output remains in the shared task payload and drives existing execution/verification checks. Thus `other` can represent a custom format without a hidden or implementation-specific conversion table.

The open OFFER's `i` value is a JSON object with exactly `schema="maxplayer.public-task.v2"`, `text` (task string), `requested_output` (original string), `dispatch` (object with only `agent`, `harness_family`, `harness_model`, `capabilities`, optional as on main), and optional `contribution` below. This entire discovery payload is deliberately public. Its semantics match the corresponding targeted encrypted task fields. Enum filter values also present in public tags must match exactly. No contradictory duplicate source is accepted. This is not a secret input channel or a post-award exchange.

**Contribution.** Keep `job-class,contribution` public, but targeted-private `target`, `base`, `accepts` values that contain repository URLs/branch names move into the initial committed task's `contribution` object. Exact object keys: `target_owner_pubkey` (H32), `target_clone_url` (HTTPS string), `base_branch` (valid Git ref string), `base_oid` (OID), `accepts=["fork"]`, and `input` (the pinned job-repo manifest entry when imported). Reject unknown/duplicate keys and any partial pin. Preserve owner/base/parentage and authorship verification; private locators/branches stay inside content. Open contribution details live in `i.contribution`, accessible before claim. Do not publish descriptive target/base tags outside that intentionally public task. `sig,seller-contribution` remains on RESULT; reconstruct and verify its exact main contribution tuple using the decoded offer and verified fork artifact. No tuple components are dropped or replaced with untrusted seller echoes. RESULT's public contribution offer-echo tags are forbidden; authority is the decoded signed OFFER, not those redundant echoes. Preserve the existing contribution signature bytes exactly: compact JSON array `["maxplayer/v1/contribution-tuple", offer_event_id, seller_pubkey, target_owner_pubkey, target_clone_url, base_oid, result_repo, result_branch, result_commit_oid]`, SHA256 then Schnorr signature. Its legacy `job_id` slot means OFFER event ID, not random v2 routing ID; there is no need to change that domain when the semantics remain identical.

**Invoice.** `creq` is an invoice, not a payment token or private key. Preserve the signed claim's exact original request bytes for hashing/payment. For private-mode publication parse the supported NUT-18 representation with main's decoder, accept only its standard routing/payment fields, require amount/unit/mints/recipient transport consistent with the claim, and forbid optional description/memo text or unknown extension fields. Reject an unsuitable request before signing the CLAIM; never sanitize an already signed request and pretend its hash is unchanged. NIP-17 payment payload recipient policy remains separate; invoice processing does not make payment secrets part of the content channel. Exact decoded request keys: `i` is the root OFFER event ID (H32), `a` is the offer amount, `u="sat"`, `s=true`, `m` is a nonempty unique list of approved Mint values, `d` is absent or null, `t` is a one-element transport array, `nut10` absent or null. Transport has exactly `t="nostr"`, `a` a canonical nprofile for the claim-author key with **no relay hints or extra TLVs**, and `g=[["n","17"]]`. No other map keys, duplicate map keys, transport tags or trailing encoded data are accepted. This is the current seller builder's shape (`gateway.rs:1445 @135e4ea`), not a new payment-recipient policy. Validate the raw CBOR/decoded map before permissive serde parsing; `creqA` and supported `creqB` encodings must yield that same closed shape. Limit the encoded request to 16 KiB and at most 32 mints. The pinned Cashu `nut18/payment_request.rs` and `transport.rs` define the renamed fields; default serde unknown-field handling is insufficient.

**Numeric execution metadata.** Initial private schema permits only `wall_time,<U64>,ms` (0..1), and `tokens,<U64>,input|output|total` (0..1 per qualifier). If present, also require exactly one `metadata_trust,seller-claimed`. Omit both trust tag and numeric block when absent. RESULT and RECEIPT are the only carriers; receipt may echo only exact values from its referenced RESULT. Free-form `harness`, `model`, `usage_transport`, `cost` basis/labels and all other execution rows stay in encrypted RESULT metadata or are absent; this does not alter the buyer's original capability filters. These metadata remain seller-claimed and excluded from the receipt co-signature as on main.

## 3. Exact delivery and settlement binding

### 3.1 RESULT bodies and the same verified object

Every RESULT's `award` refers to the buyer-authored award of the seller's claim for the root OFFER. Reject another claim/award/seller, amount, output, job ID or task commitment. Do not decide this from tag shape alone.

- **Private Git:** RESULT `content=""`. Fetch the exact `repo`/`branch`/`commit` under job ACL, verify parentage/sentinel and contribution tuple as on main. `delivery_integrity_hash` is the buyer-verified commit OID; `delivery_kind="fork"`. Optional encrypted answer/review text is bound by its content pair and event signature but does not substitute for verified Git bytes.
- **Private inline:** RESULT `content=""`; encrypted body type `answer` holds the marked answer text and any review/metadata. `delivery_integrity_hash` is exactly the RESULT's salted `content-commitment`; `delivery_kind="inline"`. Buyer independently decrypts/recomputes that commitment, validates the answer marker/eligibility, then materializes only the answer text. Do not fall back to SHA256(plaintext), hash base64 text, or accept a claimed commitment without the body.
- **Public v2 inline:** RESULT `content` is the exact JSON envelope `{schema:"maxplayer.content-envelope.v2",nonce:<64-hex>,body_b64:<base64>}` specified in the parent spec. Its decoded body type is `answer`; its text is intentionally public. RESULT carries the same content pair and exact commitment construction as private inline. No receiver-specific encryption is applied here. The preserved body bytes, not a reserialized body, define the digest. Repo/branch/commit are absent.
- **Public v2 Git:** existing public Git result content stays public; its verified delivery identity is the commit OID, with `delivery_kind="fork"`. No private-mode field restriction is silently applied to public jobs.

Inline remains only for the existing empty-snapshot, marked-answer, from-scratch eligible path. Contribution work never settles inline. No new result/review stage is introduced.

### 3.2 ACCEPT stays job-level; local bind is result-specific

**Do not add a result reference to public ACCEPT in this scope.** Its exact rows are §2.3 and its interpretation remains `docs/protocol-v1.md:686 @135e4ea`: a public observer cannot identify the accepted result from ACCEPT alone when several exist. State this limitation rather than claiming a trustless result-specific ACCEPT.

Before publishing ACCEPT, atomically persist the existing durable local pay-bind with exact `offer_id`, `claim_id`, selected `award_id`, `result_id`, buyer/seller, payment mode/amount/unit, realized mint and `creq_hash` for paid jobs, `job_hash`, `delivery_kind`, verified `delivery_integrity_hash`, and the original seller signature, random routing job ID, accepted mint set and delivery-specific immutable evidence (Git locator/ref/OID plus contribution binds/signature; or inline content ID/envelope bytes/commitment plus extracted answer). These are existing pay-bind facts plus the v2 privacy evidence needed to reconstruct verification, not a new public message. Resume/retry reads this record, never “latest result,” a changed default mint, or fresh decrypted content under an old ID.

RECEIPT already has `["e",result_id,"","reply"]`; require it to match this bind and its result's exact integrity/kind. The buyer's event-level signature authenticates that reference. Public ACCEPT remains ambiguous by design; the later receipt and local verifier are not.

### 3.3 Co-signed receipt preimage

Use the existing `ReceiptPreimage::canonical_json` construction (`crates/maxplayer-core/src/receipt.rs:90 @135e4ea`), with v2 domain and the precise v2 delivery identity above:

```text
["maxplayer/v2/receipt-preimage",
 job_hash, offer_id, amount_integer, "sat", buyer_pubkey, seller_pubkey,
 delivery_integrity_hash, delivery_kind, "none", creq_hash]
```

Canonical encoding is compact UTF-8 JSON array in this exact order, no whitespace or trailing newline; all hash/key/kind strings are validated ASCII, amount is a JSON integer. SHA256 of those bytes is the Schnorr message signed by both parties. `job_hash` is exactly the parent spec's domain-separated hash of the OFFER ID. Paid jobs require `creq_hash=SHA256(exact signed-CLAIM creq UTF-8 bytes)` as the final array element. The realized mint is **not** in the preimage: as on main it must belong to the accepted invoice set and be pinned in the local pay-bind. Execution metadata commitment remains literal `"none"`; numeric public echoes do not become co-signed facts.

`result_id` is **not** in this preimage: the seller signature is inside RESULT, so including RESULT's future ID would be circular. It stays in the buyer-signed receipt's reply tag and local bind. Award/claim validation is mandatory outside the preimage; `offer_id`, party keys, invoice hash and verified delivery identity prevent treating another trade's cosignature as authority. Do not add a self-referential signature to the answer envelope.

For `payment=none`, preserve main: no payment attempt and no paid RECEIPT. If the existing free RESULT verification path carries a seller artifact signature, it uses the same array with the **final creq_hash element omitted**, never null/empty/dummy invoice. The absent paid step is not permission to bypass answer/Git verification. Never produce an artificial zero-sat receipt.

### 3.4 Required cross-implementation vectors and negative tests

Before implementation is enabled, publish shared vectors for exact body/envelope bytes, nonce, content commitment, OFFER/job hash, Git and inline preimage JSON/digest, seller/buyer signatures, paid/free variants, and public-inline materialized text. Verify sender and buyer independently reproduce these bytes. Do not infer interoperability from identical helper calls alone.

Required negatives: two RESULTS A/B with different artifacts and identical job/claim; only persisted verified A can be paid after restart, and receipt must name A. Swapping B's ID, OID/commitment, kind, signatures, claim/invoice, amount, mint or party key must fail the corresponding bind/preimage/mint check. Republishing identical artifacts under a second result ID must not create a second payment; preserve the existing pay-once fences. Wrong carrier author/type/phase, task changes under an existing claim, cross-candidate details, injected unknown tags/subkeys, invalid enum values, duplicate singleton fields and altered numeric qualifiers are rejected. Mutate **each permitted public field**; a seeded-plaintext search alone is insufficient.

## 4. Job identity and review disposition

Provisioning reserves `(tenant,buyer_pubkey,job_id)` for exactly one signed OFFER ID and its content commitment/mode. Validate the signed offer before first reservation. Repeating identical offer bytes is idempotent; any other offer under the same key is `409` and gains no access, even before award or after closure. Buyer/client checks mirror this rule; randomness is not a replacement for uniqueness. Never recycle an old job ID for a replacement offer. This makes initial `offer_id=null` safe only in conjunction with the single pinned signed OFFER and commitment checks.

Review findings resolved here: §1 existing-author mapping/no standalone followup/review; §2 closed private field schema; §3 exact inline/receipt encoding and explicit unchanged ACCEPT limitation; §4 job-ID reuse. Diagram's targeted pre-claim read access is clarified in its guide. No new product choices, lifecycle stages, service ACK or post-award input exchange are introduced.
